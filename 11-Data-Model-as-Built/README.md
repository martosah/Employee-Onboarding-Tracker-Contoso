# 11. Data Model as Built

Section 6 presented the entity relationship diagram as a design. This section records how that design became real Dataverse tables — the columns, the relationships and their delete behaviour, and the modelling decisions that matter when the system runs.

For the visual model, see the ERD in [Section 6](../06-Entity-Relationship-Diagram).

---

## Table Classification

The nine custom tables fall into three tiers. This ordering also drove the build sequence — reference tables first (nothing depends on them being populated), then master data, then the transactional tables that tie everything together.

| Tier | Tables | Role |
| --- | --- | --- |
| Reference | Department, Job Role, Staff, Task Template | Slow-changing lookups and the onboarding checklist library |
| Master data | Employee | The person being onboarded |
| Transactional | Onboarding Record, Onboarding Task, New Hire Document, Equipment | The live onboarding activity |

---

## The Hub — Onboarding Record

One Onboarding Record exists per new hire. It is the parent of that hire's tasks and documents, and the table the whole solution revolves around.

| Column | Type | Notes |
| --- | --- | --- |
| Record Number | Autonumber | Primary name, `REC-001` format |
| Employee | Lookup → Employee | The new hire this record is for |
| Record Status | Choice | Not Started / In Progress / At Risk / Completed |
| Day 1 Readiness | Choice | Pending / Ready / At Risk |
| Record Opened Date | Date & time | When onboarding began |
| Record Closed Date | Date & time | Set on completion |
| Assigned HRBP | Lookup → Staff | The HR Business Partner who owns the record |
| Probation Outcome | Choice | Manager's decision at the 90-day mark |
| Preparation Lead Time (Days) | Whole number | Days between record opened and start date — added in Phase 2 (see Section 15) |
| Total Tasks | Rollup | Count of related tasks |
| Completed Tasks | Rollup | Count of related completed tasks |

The two rollup columns let the form and views show progress (e.g. 7 of 13 complete) without a flow having to maintain a counter.

## Employee — Master Data

The person record. Created when an offer is accepted; the Onboarding Record is then created against it.

| Column | Type | Notes |
| --- | --- | --- |
| Employee Number | Autonumber | Primary name, `EMP-001` format |
| Full Name | Text | |
| Start Date | Date & time | Drives every task due date and the readiness check |
| Job Role | Lookup → Job Role | Determines which role-specific tasks generate |
| Department | Lookup → Department | |
| Employment Type | Choice | Full-time / Part-time / Contract |
| Work Location | Text | Used by operations for equipment delivery |
| Reporting Manager | Lookup → Staff | Owns the probation milestones |
| Personal Email | Text (Email) | Confidential — flagged for column security (see Section 14) |
| Work Email | Text (Email) | Blank until IT provisions the account |

## Task Template — The Generation Engine

The standard onboarding checklist lives here as data, not code. HR can change what gets generated by editing rows in this table — no developer involvement.

| Column | Type | Notes |
| --- | --- | --- |
| Task Name | Text | Primary name (e.g. "Prepare Laptop") |
| Template Code | Autonumber | `TPL-001` format |
| Default Assignee Role | Choice (Staff Role) | Which role performs this task |
| Due Date Offset Days | Whole number | Days relative to start date; **negative means before** (e.g. `-3` = three days pre-start) |
| Is Critical For Day 1 | Yes/No | If yes, must be complete for Day-1 Readiness to pass |
| Applies To Job Role | Lookup → Job Role | If set, generates only for that role; if blank, generates for everyone |
| Requires Equipment | Yes/No | Flags tasks that involve issuing equipment |

Three columns here carry most of the system's intelligence. **Due Date Offset Days** lets the same template produce a correct due date for any hire by anchoring to their start date. **Applies To Job Role** is what makes generation role-aware — a "Configure developer tools" template only fires for developers. **Is Critical For Day 1** is what the readiness check counts.

## Onboarding Task

The individual work items, generated from templates against a specific Onboarding Record.

| Column | Type | Notes |
| --- | --- | --- |
| Task Number | Autonumber | `TSK-0001` format |
| Task Name | Text | Copied from the template at generation |
| Onboarding Record | Lookup → Onboarding Record | **Parental** — the task belongs to the record |
| Assigned To | Lookup → Staff | The owner who performs the task |
| Completed By | Lookup → Staff | Who actually completed it |
| Task Template | Lookup → Task Template | The template it was generated from |
| Task Due Date | Date & time | Calculated from start date + offset |
| Status | Choice | Not Started / In Progress / Completed |
| Is Critical For Day 1 | Yes/No | Carried from the template |

New-hire context on the task form — start date, preparation lead time, record status, and Day-1 readiness — is surfaced through a **Quick View form** drawn from the parent Onboarding Record and Employee, rather than being copied into columns on the task. This keeps a single source of truth and avoids stale duplicated data; the trade-off (it requires task assignees to have read access to the parent record) is discussed in Section 14.

## Supporting Tables

| Table | Purpose | Notable columns |
| --- | --- | --- |
| Department | Organisational units | Primary name |
| Job Role | Role catalogue | Primary name |
| Staff | Internal people who perform onboarding work | Backup Staff (self-reference), App User (lookup → User), Staff Role |
| New Hire Document | Documents uploaded for a hire | **Parental** to Onboarding Record; Document Type; Document Status |
| Equipment | Assets issued to a hire | Issued By, Related Task, Assigned To (Employee) |

The **App User** column on Staff is a deliberate design choice covered in Section 12 — it stores each staff member's system-user identity so flows can set task ownership reliably.

## Relationships and Delete Behaviour

Most relationships use the Dataverse default (Referential + Restrict), which is correct — it prevents deleting a Job Role that employees still point to, for example. Only eight relationships were changed from the default, and each change is intentional.

| Child table | Lookup | Behaviour set | Why |
| --- | --- | --- | --- |
| Onboarding Task | Onboarding Record | **Parental** | Deleting a record removes its tasks; the task can't outlive its parent |
| New Hire Document | Onboarding Record | **Parental** | Documents belong to the record |
| Onboarding Task | Task Template | Remove Link | A template can be retired without blocking or deleting historical tasks |
| Onboarding Task | Completed By | Remove Link | A staff member can leave without orphaning task history |
| Equipment | Issued By | Remove Link | Same — staff departure shouldn't block equipment records |
| Equipment | Related Task | Remove Link | A task can be removed without deleting the equipment record |
| Staff | Backup Staff (self-ref) | Remove Link | Removing a backup shouldn't cascade-delete the primary |
| Task Template | Applies To Job Role | Remove Link | A role can be renamed/retired; templates survive |

The distinction in plain terms: **Parental** means the child cannot exist without the parent (delete the record, the tasks go with it). **Remove Link** means the reference is simply cleared if the target is deleted, so cross-table lookups never block a deletion or leave a dangling pointer.

## Keys and Identity

**Autonumber primary names** give every transactional record a human-readable identifier (`REC-`, `EMP-`, `TSK-`, `TPL-`). A build lesson worth recording: autonumber columns are set to **Optional**, not Business Required — marking an autonumber as required creates a save-blocking deadlock, because the value isn't assigned until the row is committed.

**Alternate keys** were added on Employee Number and Template Code to enforce uniqueness and to allow records to be referenced by their business key rather than only their internal GUID.

---

## Design Decisions That Matter

A few choices shape how the model behaves and are called out here so a reviewer doesn't have to infer them:

**Start Date lives on Employee, not Onboarding Record.** Every due date and the readiness check read it from the related Employee. This avoids duplicating the date and keeps it authoritative.

**Configuration lives in data, not logic.** The onboarding checklist is rows in Task Template; the readiness threshold and notification settings are environment variables. HR changes behaviour by editing data, not by reopening flows.

**Parental cascade has an ownership side effect.** Because Onboarding Record → Onboarding Task is parental, changing the parent record's owner cascades to its child tasks. This directly affected the build: task ownership must be assigned in automation *before* the parent's owner is set, or the parent's owner overwrites every task owner. The flow is sequenced accordingly (see Section 12).
